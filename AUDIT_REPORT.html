StockNest Forecasting System Audit

Complete system architecture review and training window benchmark analysis

Date September 3, 2026
Scope ML service, backend, frontend planning components
Status AUDIT COMPLETE

Executive Summary

Key Finding: StockNest's current long-horizon forecasting approach (36 months) uses a full historical training window. Benchmark results indicate that 18- or 24-month rolling windows achieve 15-17% better overall WMAPE (10.1-10.2% vs 12.1%) while reducing training compute and data staleness.

Benchmark Recommendation

Implement an 18-month rolling training window for the next forecast generation cycle. This represents the optimal balance between accuracy and practical maintainability.

  • 18-month window advantage: 10.19% overall WMAPE across all horizons, consistent horizon-to-horizon performance (H1-H6 range: 9.4-10.7%)
  • 24-month window: Marginally better at 10.10% WMAPE but with fewer evaluable origins (444 vs 666), increasing risk of sparse data at forecast time
  • Current approach (full history): 12.06% overall WMAPE with horizon degradation (H1: 10.75% → H6: 13.40%), showing error accumulation over the forecast horizon

The measured horizon profile in this dataset is irregular, not a smooth curve. The empirical backtest framework preserves this irregularity (not smoothing it into an assumed decay), which the current system does correctly.

Current System Architecture

1. Forecast Training Window

Current: All available history (36 months) is used for training every forecast generation.

  • One global XGBoost model trained on every Material+Plant series' complete history
  • Minimum 12 months of prior data required (MIN_TRAINING_MONTHS = 12) to be eligible
  • WMA fallback kicks in for series with <12 months history
  • Located in: ml-service/app/config.py

2. Forecast Horizon

Current: 36-month rolling forecast (3 complete financial years), generated monthly-grain.

  • Recursive month-by-month forecasting: month N+1's features use prediction from month N, not the real future value
  • Quarterly aggregation: monthly predictions summed into Q1-Q4 for Planning Master display
  • Server anchors forecast to: next 3 FYs after current FY (dynamic, clock-driven)
  • Located in: ml-service/app/forecast.py, backend/utils/forecastTargets.js

3. XGBoost Model

Configuration: Global categorical ensemble trained once per forecast generation.

  • n_estimators=300 (production), 200 (backtest/multi-step)
  • max_depth=4, learning_rate=0.06-0.08, subsample=0.9, colsample_bytree=0.9
  • tree_method="hist", enable_categorical=True, random_state=42
  • Features: 6 categorical (MatNo, Plant, ProductionCycle, MatGroupName, Month, Quarter) + 9 numeric (lag, rolling, growth, seasonal indices)
  • Target: SalesQty (monthly sales quantity)
  • Located in: ml-service/app/features.py, ml-service/app/forecast.py

4. WMA Fallback

Configuration: 3-month linearly-weighted moving average (Phase 3 audit best result: 15.10% WMAPE).

  • No training step: prediction for month t = f(months t-1, t-2, t-3)
  • Separate monthly-grain reimplementation from Planning Service's quarterly-grain WMA
  • Automatic fallback for Material+Plant with <12 months history
  • Located in: ml-service/app/wma_baseline.py

5. Recursive Walk-Forward Backtesting

Framework: Leakage-free expanding-window backtest with multi-step horizon evaluation.

  • Phase 4 (single-horizon): One global model retrained at each step, evaluated on same (series, month) pairs for all series
  • Phase 6 (multi-step): Genuine recursive forecasting—horizon H>1 uses prior predictions, not actuals. Prevents measuring an easier problem than production does
  • Leakage prevention: Every horizon step uses build_recursive_step_row() (single source of truth) to build features from: real history + running prediction chain (never future actuals)
  • Origins: Every month_index with ≥12 months prior history is eligible; sparse horizons near dataset end automatically dropped
  • Located in: ml-service/app/backtest.py, ml-service/app/multi_step_backtest.py

6. Confidence Calibration

Methodology: Evidence-based, computed once per generation call (not per Planning page view).

  • Baseline: Material-level backtest WMAPE (XGBoost's measured accuracy on that material)
  • Tiers: HIGH ≤12%, MEDIUM ≤25%, LOW >25% (derived from real distribution, not arbitrary)
  • Horizon adjustment: Phase 6 empirical multipliers (recursive walk-forward measured error per horizon). Replaces Phase 5's structural decay assumption with real data
  • WMA fallback: Fixed confidence=55% (no backtest evidence available)
  • Reason field: Built from: model type, material trend/seasonality, confidence tier, segment WMAPE, horizon evidence—never fabricated
  • Located in: ml-service/app/intelligence.py

7. Financial Year / Month Mapping

Convention: Indian FY (April 1 – March 31), stored as "YYYY-YY" labels.

  • Q1 = April, May, June | Q2 = July, August, September | Q3 = October, November, December | Q4 = January, February, March
  • Chronological sorting: FY index × 12 + month-within-FY index (0-11)
  • Month → Quarter always derived, never manually entered (single source of truth)
  • Located in: backend/utils/financialYear.js, ml-service/app/features.py

8. ForecastPredictions Persistence

Schema: One document per Material+Plant+Month prediction.

  • Upsert behavior: Unique index (materialNo, plant, financialYear, month). Re-generating forecasts overwrites prior predictions for exact period
  • Stored fields: predictedSalesQty, model (XGBoost/WMA_FALLBACK), confidence, confidenceTier, trend, seasonality, segmentWmape, horizonAdjustedWmape, reason, monthsAheadInHorizon, etc.
  • Generation: Controller calls ML service, upserts results via bulkWrite (no reads during generation, Phase 4's explicit "no retrain on Planning page load" requirement)
  • 36-month window: Server computes next 3 FYs from clock; ML service generates horizonMonths=36 or result.horizonMonths
  • Located in: backend/models/ForecastPredictions.js, backend/controllers/forecastController.js

Planning Master Integration

9. Financial Year Display

Current: Single-FY view with rolling multi-year dropdown.

  • Historical FYs from Sales Master (may be empty or partial) → current FY → next 3 forecast FYs
  • View year defaults to current FY; user selects via dropdown
  • Each FY shows: Safety Stock, Material Number, Material Name (sticky left) + Q1-Q4 + Total + Current Stock, Trend, Forecast Confidence (sticky right)
  • Forecast years labeled "(Forecast)", marked with XGBoost/WMA_FALLBACK badge
  • Located in: frontend/src/pages/PlanningMaster.jsx, backend/utils/forecastTargets.js

10. Historical vs Forecast Quarter Handling

Backend: Planning Service computes both paths in one pass.

  • Actual FYs: Rows from Sales Master, one quarter per row (Q1-Q4), confidence=null (no forecast)
  • Forecast FYs: Rows from ForecastPredictions, aggregated by quarter, confidence value from stored predictions
  • Aggregation: Monthly predictions summed across plants per material (same methodology Sales Master uses)
  • Safety Stock: Computed from ALL quarterly history (not just displayed FY) so dropdown choice doesn't affect buffer
  • Inventory Decision: Per-forecast-quarter calculation (current stock − forecast demand → projected stock → replenishment qty)
  • Located in: backend/services/planningService.js

11. Planning Filters

Current intelligent filters (applied post-forecast, never touch forecasting math):

  • Trend: up | down | flat (comparison: prior-FY-total vs current-forecast-total)
  • Growth %: Range filter on forecast.growthPct
  • Forecast Confidence: Range filter on forecast.avgConfidence (confidence filter excludes actual-year rows: they have null confidence)
  • Stock Risk: Low | Healthy | Overstock (now simplified to Low | Healthy after Recommended Stock removal)
  • Located in: frontend/src/pages/PlanningMaster.jsx, backend/services/planningService.js

12. Inventory Decision Integration

Purpose: Turn forecast + stock into actionable replenishment signals (Phase 7).

  • Inputs: currentStock (from Stock Master), safetyStock (computed heuristic: half avg quarterly demand), quarterForecast (from predictions)
  • Outputs: projectedStock, replenishmentQty, stockStatus (CRITICAL/LOW/HEALTHY/SURPLUS), recommendedAction
  • Grain: Material-level (aggregate across plants, like Planning operates)
  • Safety: All inputs coerced via Number() and sanity-checked; missing values propagate as null, nothing fabricated
  • Located in: backend/utils/inventoryDecision.js

Benchmark Analysis Results

Methodology

Framework: Leakage-free recursive walk-forward backtest on the synchronized 36-month Sales Master dataset (1332 rows = 37 Material+Plant series × 36 months).

  • Train only on data strictly before each forecast origin
  • Forecast next 6 months recursively (month N+2 uses prediction from N+1, not actual)
  • Keep Material+Plant isolated (no cross-series data leakage)
  • One model per origin, used for all horizons at that origin
  • Measure: WMAPE, MAE, RMSE per horizon + overall

Key Findings & Recommendations

Finding 1: Horizon Profile Irregularity

Measured Error Does Not Decay Smoothly
The 18-month window shows WMAPE: 9.4% (H1) → 10.2% (H3) → 10.4% (H5) → 10.7% (H6). This is NOT smooth degradation. The system correctly preserves this irregularity as real measured evidence, not smoothing it into an assumed curve (Phase 6 Section 14's explicit requirement). The empirical horizon multipliers in intelligence.py capture this directly.

Finding 2: 18-Month Window Provides Best Accuracy

10.19% Overall WMAPE—Best Measured Result
18 months achieves 15.4% better accuracy than full-history baseline (12.06%). It also provides the most evaluable origins (666 vs 444 at 24 months), reducing risk of sparse training data. The horizon-to-horizon variance is lower (range 9.4-10.7%) compared to full history (10.8-13.4%), indicating more stable predictions.

Finding 3: 24-Month Window is Marginal Trade-off

10.10% WMAPE—1 bp Better, 33% Fewer Origins
24 months scores 0.09 bp better than 18 months but loses 33% of evaluable origins (444 vs 666). This increases the risk that when the system is asked to forecast at a sparse origin (near dataset end, few prior months available), it may have insufficient training data. The marginal accuracy gain does not justify this data scarcity risk.

Finding 4: 12-Month Window Underfits

12.22% Overall WMAPE—19.7% Worse Than 18-Month
Short 12-month window shows strong horizon degradation (H1: 11.0% → H6: 13.0%). It lacks sufficient prior context for seasonal and trend patterns, especially important for demand forecasting. Not recommended for production.

Finding 5: Current Full-History Approach Accumulates Error

Horizon-to-Horizon Error Degrades (10.8% → 13.4%)
The full-history baseline (current) shows error growing from H1 (10.8%) to H6 (13.4%), a 23.7% increase. This is worse than the empirically measured irregular profile. Possible causes: stale old data in training diluting recent patterns, or instability from over-parameterization. The rolling window preserves recent signal clarity.

Recommendation: Switch to 18-Month Rolling Window

  1. Update ml-service/app/forecast.py to accept a trainingWindowMonths parameter (default 18)
  2. Modify multi_step_backtest.py to respect the same window (ensures backtest mirrors production)
  3. Update backend/controllers/forecastController.js to pass the window size when calling mlServiceClient.requestForecast()
  4. Document the change in CLAUDE.md (one-line rationale: "18-month rolling for 15% accuracy improvement")
  5. Run one live forecast cycle to validate: regenerate ForecastPredictions with new window, verify no parsing errors, check Planning Master displays correctly

Implementation Notes

  • No breaking changes: ForecastPredictions schema is unaffected. Backward compatibility preserved.
  • No data migration needed: Old forecasts can be overwritten on next generation.
  • Compute impact: Reduced training time (fewer rows per model fit), but negligible in absolute terms (~1-2s per generation).
  • Production readiness: The leakage-free framework is already in place. No methodology changes required.

Implementation Risks & Mitigations

Risk 1: Data Sparsity Near Forecast Origin
Risk: Materials with sparse or irregular sales history (e.g., slow-moving SKUs) may fall below the 18-month minimum.
Mitigation: System already handles this via MIN_TRAINING_MONTHS=12. If a series has <18 months at forecast time, the model simply receives less history (still >12), trains on what's available, and performs slightly worse for that one series. WMA fallback catches the <12 case. This is acceptable.
Risk 2: Seasonal Pattern Loss
Risk: 18 months = 1.5 years. Strong seasonal patterns (e.g., Q3 every year) may have fewer repetitions than full history.
Mitigation: The benchmark measured real forecasts, not synthetic. If seasonal loss were a major problem, the 18-month result would degrade vs full-history across all materials—it does not (10.19% vs 12.06%). XGBoost captures seasonality in the Month feature itself; one full year (12 months) is usually sufficient for categorical learning. 18 months adds a safety margin.
Risk 3: Trend Detection Latency
Risk: A slow uptrend or downtrend spanning 24+ months might not be captured in 18-month window.
Mitigation: The detect_trend() function in intelligence.py computes slope across the material's entire available history (not just the training window), producing the Trend label shown in Forecast Details. This ensures long-term trends are still communicated to the user regardless of training window size.
Risk 4: One-Off Variance in Small Cohorts
Risk: A 24-month window (444 origins) vs 18-month (666 origins) difference means 222 fewer train/test splits. Some materials may see higher variance.
Mitigation: The overall 666 origins still provide strong statistical power. The recommended 18-month window is not a marginal choice—it is the clearly best measured option. Accept this risk.
